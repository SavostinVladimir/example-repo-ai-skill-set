# Архитектурные предложения по оптимизации топ-3 узких мест системы уведомлений

В документе представлены детальные таблицы вариантов оптимизации трех наиболее тяжеловесных сценариев работы с уведомлениями:
1. **Рекурсивная пагинация сгруппированных уведомлений (API v2)**
2. **Сбор агрегатов по группам (`load_groups_data`: счетчики и участники)**
3. **Рекурсивная проверка цепочки личных сообщений (`statuses_that_mention_sender`)**

Для каждого сценария рассмотрены:
- Текущая реализация (As-Is)
- Оптимизация средствами PostgreSQL
- Альтернативное хранение данных в Redis

---

## Сценарий 1. Рекурсивная пагинация сгруппированных уведомлений (API v2)

| Аспект | Как сделано сейчас (As-Is) | Оптимизация в PostgreSQL | Хранение данных в Redis |
| :--- | :--- | :--- | :--- |
| **Механизм** | `WITH RECURSIVE` + 40 циклов `LATERAL` сканируют `notifications` и `accounts`, на лету отбрасывая дубликаты `group_key` через `NOT group_key = ANY(wt.groups)`. | **Write-Time Grouping (таблица `notification_groups`):**<br>При создании уведомления выполняется `UPSERT` в выделенную таблицу групп `(id, account_id, group_key, updated_at)`.<br>Чтение: обычный `SELECT * FROM notification_groups WHERE account_id = $1 ORDER BY id DESC LIMIT 40`. | **Sorted Set на каждого пользователя:**<br>`ZADD user_notifications:{account_id} {timestamp_or_id} {group_key}`.<br>Чтение страницы: `ZREVRANGEBYSCORE` с лимитом 40 за $O(\log N + M)$. Данные читаются прямо из оперативной памяти. |
| **Вычислительная сложность** | $O(K \times \text{IndexScan})$, где $K$ может достигать сотен тысяч строк при вирусных постах. | $O(\log N + M)$ — классический btree index scan с `LIMIT 40`. | $O(\log N + M)$ в памяти RAM ($< 1$ мс). |
| **Нагрузка на СУБД** | Экстремальная утилизация CPU, многократное чтение одних и тех же буферов памяти, медленный p95/p99. | Минимальная: чтение 40 последовательных строк по индексу без циклов и соединений. | Нулевая нагрузка на PostgreSQL (вся нагрузка уходит в Redis). |
| **Плюсы подхода** | • Не требует изменения схемы БД.<br>• Нет избыточности данных. | • **Простота реализации:** стандартная реляционная модель без сторонних сервисов.<br>• **ACID-гарантии:** строгая согласованность групп и нотификаций.<br>• Падение задержки чтения с 200–500 мс до 1–3 мс. | • **Максимальная скорость:** время отклика $< 1$ мс при любой нагрузке.<br>• **Полная изоляция:** PostgreSQL освобождается от 100% запросов на скролл ленты.<br>• Встроенный TTL для автоматической очистки старых хвостов. |
| **Минусы подхода** | • Деградация при росте числа реакций.<br>• Невозможно эффективно кешировать. | • Дополнительная операция записи (`INSERT ... ON CONFLICT`) при генерации каждого уведомления.<br>• Необходимость миграции и начального бэкфилла данных для существующих групп. | • **Потребление оперативной памяти (RAM):** хранение сотен тысяч множеств требует контроля памяти (eviction policy).<br>• Риск рассинхронизации между Redis и PostgreSQL при сбоях воркеров.<br>• Необходимость дублирования логики фильтрации типов. |

## Сценарий 2. Сбор агрегатов по группам (`load_groups_data`)

| Аспект | Как сделано сейчас (As-Is) | Оптимизация в PostgreSQL | Хранение данных в Redis |
| :--- | :--- | :--- | :--- |
| **Механизм** | Массив `unnest($group_keys)` и 5 независимых скалярных подзапросов на каждую группу (включая честный `SELECT count(*)`). Для 40 групп выполняется 200 подзапросов к индексам. | **Материализация агрегатов в строке группы:**<br>В строке `notification_groups` хранятся поля `notifications_count (integer)` и `sample_account_ids (bigint[8])`.<br>При каждом событии счетчик инкрементируется, а автор добавляется в массив: `notifications_count = notifications_count + 1, sample_account_ids = ARRAY_PREPEND($from_account_id, sample_account_ids[1:7])`. | **Хранение метаданных группы в Redis Hash:**<br>Ключ `notif_group_data:{group_key}`.<br>Поля: `count` (число), `sample_accounts` (сериализованный массив или JSON).<br>Инкремент: `HINCRBY count 1`.<br>Чтение для страницы: одиночный `PIPELINE` или `HMGET` за $O(1)$. |
| **Вычислительная сложность** | 200 отдельных сканирований индексов + полный подсчет строк по каждой группе на странице. | $O(1)$ при чтении строки группы: данные уже лежат в извлеченной строке. | $O(1)$ на чтение хеша по ключу из памяти. |
| **Нагрузка на СУБД** | Сотни случайных обращений к страницам индекса, высокая нагрузка на дисковый ввод-вывод (Random I/O). | Отсутствует: устраняются все 200 подзапросов. Все данные отдаются в основном `SELECT * FROM notification_groups`. | Полное отсутствие нагрузки на реляционную БД. |
| **Плюсы подхода** | • Всегда 100% точные данные без риска рассинхрона счетчиков. | • **Устранение N+1 в SQL:** 0 дополнительных подзапросов.<br>• Отсутствие дорогого сканирования `COUNT(*)` для вирусных постов.<br>• Легко поддерживать средствами самого PostgreSQL (тип `bigint[]`). | • Чтение агрегатов за десятые доли миллисекунды.<br>• Атомарные быстрые инкременты (`HINCRBY`) без блокировок строк в реляционной БД.<br>• Естественное время жизни ключей (`EXPIRE` на 30–60 дней). |
| **Минусы подхода** | • Медленный рендеринг страницы (N+1 на уровне SQL-движка).<br>• Дорогой пересчет при каждом обновлении экрана. | • При удалении уведомления (отмена лайка) требуется декремент счетчика или фоновый пересчет.<br>• Чуть больший размер строки таблицы групп. | • Данные разделены между двумя системами хранения.<br>• При удалении аккаунтов или постов требуется отправлять команды очистки в Redis.<br>• При рестарте инстанса без AOF/RDB кеш нужно будет прогревать. |

## Сценарий 3. Рекурсивная проверка цепочки личных сообщений (`statuses_that_mention_sender`)

| Аспект | Как сделано сейчас (As-Is) | Оптимизация в PostgreSQL | Хранение данных в Redis |
| :--- | :--- | :--- | :--- |
| **Механизм** | Рекурсивный CTE по иерархии `in_reply_to_id` (до 100 уровней вглубь) с соединением `statuses` и `mentions` при каждом входящем DM от нового контакта. | **Денормализация права на переписку (Contact Allowlist):**<br>Факт двустороннего контакта сохраняется при первом ответе: либо флаг в существующей таблице `account_conversations`, либо запись в `notification_permissions`.<br>Проверка при входящем сообщении: `SELECT 1 FROM account_conversations WHERE account_id = $recipient AND $sender = ANY(participant_account_ids) LIMIT 1`. | **In-Memory Allowlist в Redis Set:**<br>Множество доверенных собеседников: `user_dialogs:{recipient_id}`.<br>Проверка права при получении сообщения: `SISMEMBER user_dialogs:{recipient_id} {sender_id}` за $O(1)$.<br>Добавление: `SADD` в момент отправки исходящего ответа. |
| **Вычислительная сложность** | До 100 итераций CTE по двум большим таблицам (`statuses`, `mentions`). | $O(1)$ — точечный индексный поиск по одной строке диалога. | $O(1)$ в оперативной памяти. |
| **Нагрузка на СУБД** | Случайные чтения с диска (Random Read I/O) на критическом пути записи (Write Path). Задержка обработки очереди Sidekiq. | Минимальная: один индексный SELECT за $< 1$ мс. | Нулевая нагрузка на PostgreSQL. |
| **Плюсы подхода** | • Точное следование правилу: «учитываются только ответы в рамках конкретного дерева постов». | • **Исключение рекурсивных запросов** из конвейера входящей обработки.<br>• Использование уже существующей в Mastodon модели `AccountConversation`.<br>• Простота сопровождения и полная персистентность. | • Мгновенная проверка за микросекунды ($< 0.5$ мс).<br>• Полная защита воркеров Sidekiq от просадок дискового I/O при спам-атаках в личные сообщения.<br>• Минимальный объем памяти (только числовые ID аккаунтов в Set). |
| **Минусы подхода** | • Зависание воркеров при обработке сообщений в глубоких тредах.<br>• Вымывание горячих страниц из буферного пула PostgreSQL. | • Требует аккуратной логики проставления флага при создании первого ответа в переписке.<br>• Не учитывает случаи, когда пользователь ответил в публичном треде, а затем собеседник перешел в DM (если проверять только DM-диалоги). | • Необходимость начального наполнения (warmup) множеств активных диалогов из PostgreSQL.<br>• Необходимость инвалидации множества при блокировке собеседника. |
