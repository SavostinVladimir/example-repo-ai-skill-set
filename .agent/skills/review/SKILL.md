# Скилл: /review (Мультиагентное ревью кода и спецификаций)

Этот скилл выполняет комплексное независимое ревью кода и проектных спецификаций с помощью команды специализированных суб-агентов из директории `reviewers/`, с учетом области применимости (`applies_to`), последующей агрегацией, ранжированием по критичности и финальным арбитражем находок.

---

## Пошаговое руководство исполнения

### Шаг 1. Определение скоупа проверки и контекста

1. **Идентификация цели ревью:**
   - Если пользователь передал конкретный путь, ветку или имя OpenSpec change (например, `openspec/changes/notification-system-components` или `mastodon/app/controllers/...`), использовать его.
   - Если цель не указана явно:
     - Проверь активные изменения в git (staged/unstaged diff или `git diff HEAD~1`).
     - Либо проверь последние изменения в `openspec/changes/`.
     - При неоднозначности уточни у пользователя, что именно необходимо проверить.
   - **Классификация скоупа (`code` vs `specs`):**
     - Определи, присутствуют ли в проверяемом скоупе файлы спецификаций (`openspec/specs/**`, `openspec/changes/**`: `proposal.md`, `design.md`, `specs/**/*.md`, `tasks.md`).
     - Если в скоупе есть только код без спецификаций (`scope = code`), ревьюверы с `applies_to: ["specs"]` (`spec-goal`, `spec-undetail`, `spec-claims`, `spec-coder`) **не запускаются**.
     - Если в скоупе есть спецификации (`scope = specs` или комбинированный diff с изменениями спецификаций), подключаются как универсальные ревьюверы, так и ревьюверы спецификаций (передавая им для ревью **только** файлы спецификаций).
2. **Загрузка контекстных документов:**
   - Архитектурные решения: [ADR.md](ADR.md).
   - База известных ложных находок: [known-review-gaps.md](known-review-gaps.md).
   - Спецификации: файлы из `openspec/specs/` и `openspec/changes/*/specs/` (а также `proposal.md`, `design.md`, `tasks.md` в проверяемом change).

### Шаг 3. Запуск суб-агентов ревью

Для каждого отобранного по скоупу ревьювера запусти отдельного суб-агента с помощью инструмента `invoke_subagent` (или через `run_workflow` для параллельного запуска):

1. **Суб-агент 1: PostgreSQL & Codebase Reviewer**
   - **Role**: `PostgreSQL & Codebase Reviewer`
   - **Prompt**:
     > Проведи ревью кода и изменений базы данных в соответствии с инструкциями из [reviewers/postgresql-codebase-reviewer.md](reviewers/postgresql-codebase-reviewer.md).  
     > **Область проверки**: [список файлов/diff].  
     > **Фокус**: функциональная корректность, N+1 запросы, индексы, блокировки транзакций, обработка ошибок, идиоматичность реализации.  
     > Верни структурированный список находок в формате JSON/Markdown с указанием точных строк и фрагментов кода.

2. **Суб-агент 2: User Journey & Spec Compliance Reviewer**
   - **Role**: `User Journey & Spec Compliance Reviewer`
   - **Prompt**:
     > Проведи сверку со спецификациями и пользовательскими сценариями в соответствии с инструкциями из [reviewers/user-journey-spec-compliance-reviewer.md](reviewers/user-journey-spec-compliance-reviewer.md).  
     > **Область проверки**: [спецификации OpenSpec, ADR.md, контроллеры/сериализаторы].  
     > **Фокус**: соответствие OpenSpec и ADR, целостность пользовательских сценариев нотификаций, клиентские регрессии (обратная совместимость API, формат JSON, заголовки Link).  
     > Верни структурированный список находок.

3. **Суб-агент 3: Critical Architecture Adversary (Red Team)**
   - **Role**: `Critical Architecture Adversary`
   - **Prompt**:
     > Проведи враждебный архитектурный стресс-тест в соответствии с инструкциями из [reviewers/critical-architecture-adversary.md](reviewers/critical-architecture-adversary.md).  
     > **Область проверки**: [архитектурные решения, спеки, фоновые воркеры, код].  
     > **Фокус**: поиск причин, почему решения "в лоб" упадут под нагрузкой (вирусный фанаут нотификаций, исчерпание пулов коннектов, состояния гонки, дедлоки, каскадные сбои).  
     > Верни структурированный список находок.

> **Важно:** Суб-агенты 4–8 ниже запускаются **только при ревью спецификаций** (когда в скоупе присутствуют файлы из `openspec/`). В качестве объекта ревью им передаются **исключительно файлы спецификаций** (`proposal.md`, `design.md`, `specs/**/*.md`, `tasks.md`); кодовая база `mastodon/` и `ADR.md` используются ими только как эталон для проверки фактов и технической реализуемости. При ревью исключительно кода эти 5 агентов не запускаются.

### Шаг 4. Агрегация и формирование приоритезированного отчета

1. Собери находки от всех завершивших работу суб-агентов.
2. Проведи дедупликацию (если несколько агентов подсветили одну проблему с разных сторон — объедини их, сохранив аргументы обоих).
3. Отсортируй находки по уровню критичности:
   1. `Blocker` (Блокирует работу/мерж, приводит к фатальным сбоям данных)
   2. `Critical` (Критический риск безопасности, деградация производительности)
   3. `Major` (Нарушение контракта спеки, утечка ресурсов, риск регрессии)
   4. `Minor` (Неоптимальность, шероховатость стиля, неполнота теста)
   5. `Info` (Рекомендация по улучшению)
4. Сформируй промежуточный сводный отчет.

### Шаг 5. Запуск финального ревьювера для классификации дефектов

Прочитай инструкции из [reviewers/final-triage-reviewer.md](reviewers/final-triage-reviewer.md) и запусти суб-агента `Final Reviewer & Defect Triage Arbiter`.

**Промпт финального ревьювера включает:**
- Полный сводный отчет находок из Шага 4.
- Данные `git diff` и историю изменений (`git blame` / даты коммитов).
- Ссылку на базу известных ложных находок: [known-review-gaps.md](known-review-gaps.md).
- **Строгое требование**: Каждая находка должна быть отнесена к одной из трех категорий:
  1. 🔴 **Реальный новый дефект**: привнесен непосредственно проверяемыми изменениями в коде/спеке.
  2. 🟡 **уже существовавший старый дефект**: присутствовал в кодовой базе до текущих изменений (подтверждено git blame/историей).
  3. ⚪ **сомнительный дефект, требуется валидация**: ложное срабатывание (включая записи из `known-review-gaps.md`), стилистический спор или архитектурный компромисс, требующий подтверждения человека.
- Для каждой находки агент обязан привести **фактологическое обоснование** (Justification) со ссылкой на строки, коммиты или текст спеки.

### Шаг 6. Презентация итогового отчета пользователю

Сформируй и представь пользователю итоговый Markdown-отчет:

1. **Сводная статистика**:
   - Общее число находок.
   - Количество по категориям: 🔴 Новые, 🟡 Старые, ⚪ Сомнительные.
2. **Сводная таблица классификации**:
   - `ID` | `Критичность` | `Категория классификации` | `Файл и строки` | `Название` | `Вердикт`
3. **Детальные карточки дефектов** (сгруппированные по категориям):
   - Фактологическое обоснование от финального ревьювера.
   - Конкретная рекомендация по исправлению.
4. **Action Plan**:
   - Список немедленных исправлений (только 🔴 Реальные новые дефекты).
   - Элементы бэклога (🟡 Уже существовавшие дефекты).
   - Вопросы для согласования с командой (⚪ Сомнительные дефекты).
