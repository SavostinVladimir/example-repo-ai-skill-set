## Context

Уведомления являются центральным нервом платформы, связывающим активность пользователей (лайки, репосты, ответы, подписки, голосования) с вниманием получателей. В высоконагруженной распределенной системе обработка уведомлений не может происходить синхронно в HTTP-запросе: это привело бы к блокировкам веб-воркеров, каскадным сбоям и деградации времени отклика.

Архитектура системы строится вокруг разделения ответственности: клиенты получают мгновенный отклик, первичное действие надежно сохраняется в БД, а генерация, фильтрация, агрегация и многоканальная рассылка нотификаций выносятся в асинхронный конвейер.

Данный документ фиксирует высокоуровневый дизайн компонентов системы для внутриинстансного (Local-to-Local) жизненного цикла нотификаций без углубления в код конкретных классов и структур таблиц.

## Goals / Non-Goals

**Goals:**
- **Универсальность этапов конвейера**: Единая схема прохождения для всех типов нотификаций (реакции, репосты, меншены, фолловы, опросы, модерационные алерты).
- **Четкое разграничение зон ответственности**: Каждый компонент имеет одну главную обязанность и строго определенный вход/выход.
- **Отказоустойчивость и локализация сбоев**: Падение стриминг-сервера или сетевые тайм-ауты внешних шлюзов (WebPush/APNs/SMTP) не должны влиять на сохранение данных и первичные действия пользователей.
- **Гарантии приватности и безопасности**: Проверки черных списков (blocks), скрытия (mutes) и политик входящих сообщений изолированы в специализированном слое оценки правил.

**Non-Goals:**
- Детали федеративного протокола ActivityPub (взаимодействие с внешними серверами исключено из скоупа).
- Низкоуровневые SQL-схемы, миграции и физическая структура индексов.
- Дизайн конкретных экранов мобильных и веб-приложений (рассматривается логическое поведение клиента).

## Decisions

### 1. Архитектурное разделение конвейера на 5 сквозных этапов
* **Решение**: Прохождение любой нотификации делится на 5 обязательных фаз:
  1. *Фаза 1: Ingestion & Fast Acknowledgment* (прием события, фиксация факта действия, немедленный ответ клиенту).
  2. *Фаза 2: Asynchronous Enqueueing* (постановка в очередь с гарантией at-least-once).
  3. *Фаза 3: Policy Evaluation & Deduplication* (проверка блокировок, спам-фильтров, отсечение дублей).
  4. *Фаза 4: Grouping & State Persistence* (вычисление ключа агрегации и запись в хранилище).
  5. *Фаза 5: Multi-Channel Fan-Out* (веерная рассылка: WebSockets для онлайн-клиентов, WebPush/APNs для мобильных устройств, транзакционная почта с отложенной отправкой).
* **Альтернативы**: Синхронная генерация нотификаций при выполнении действия. Отклонено: блокирует HTTP-воркеры при массовых действиях и снижает доступность API.

### 2. Модель ответственности компонентов верхнего уровня

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                       ВЕРХНЕУРОВНЕВАЯ МОДЕЛЬ КОМПОНЕНТОВ                    │
└─────────────────────────────────────────────────────────────────────────────┘

 [ Client Layer ]              [ API & Ingestion ]           [ Queue & Workers ]
 ┌──────────────┐              ┌─────────────────┐           ┌─────────────────┐
 │ Web & Mobile │──(HTTP POST)─▶   API Gateway   │─(Enqueue)─▶   Async Queue   │
 │   Clients    │◀─(HTTP 200)──│   & Ingestion   │           │    (Broker)     │
 └──────┬───────┘              └─────────────────┘           └────────┬────────┘
        │                                                             │
        │ (Subscribe)                                                 ▼
        │                                                    ┌─────────────────┐
        │                      [ Transport Layer ]           │  Notification   │
        │                      ┌─────────────────┐           │     Engine      │
        │                      │   Real-Time     │◀─(Pub/Sub)│ (Policy/Filter/ │
        ├───────(WebSocket)────│   Streaming     │           │    Grouping)    │
        │                      └─────────────────┘           └────────┬────────┘
        │                                                             │
        │                      ┌─────────────────┐                    │
        │                      │ Push / Email    │◀─(Worker job)──────┤
        └───────(Push / OS)────│     Gateway     │                    ▼
                               └─────────────────┘           ┌─────────────────┐
                                                             │   Persistence   │
                                                             │     Storage     │
                                                             └─────────────────┘
```

1. **Client Component**:
   * *Ответственность*: Запуск действия, реализация Optimistic UI, прием real-time событий по постоянному соединению, локальное обновление счетчиков, запросы пагинации списка уведомлений.
   * *Ожидание*: Не выполняет серверных расчетов; корректно откатывает оптимистичные изменения при ошибках сети.

2. **API & Ingestion Component**:
   * *Ответственность*: Авторизация инициатора, валидация входных данных, атомарная запись базового действия, мгновенная постановка задачи в очередь фоновой обработки.
   * *Ожидание*: Время ответа P99 < 50ms; изоляция от логики доставки уведомлений.

3. **Queue & Broker Component**:
   * *Ответственность*: Надежная буферизация задач (At-least-once), управление повторными попытками при сбоях (exponential backoff), разделение очередей по приоритетам (критичные системные алерты vs массовые реакции).
   * *Ожидание*: Задержка нахождения задачи в очереди < 100ms в штатном режиме.

4. **Notification Engine (Policy, Filter, Grouping)**:
   * *Ответственность*: Центральный вычислительный узел. Оценивает правила приватности (Drop conditions), проверяет фильтры доверия (Filter conditions/Notification Requests), производит дедупликацию, рассчитывает `group_key` для агрегации множественных реакций.
   * *Ожидание*: Идемпотентность (повторный запуск воркера гарантированно не создает дублирующее уведомление).

5. **Persistence Storage Component**:
   * *Ответственность*: Персистентное хранение уведомлений, их групп и статусов прочтения; обеспечение эффективных выборок по получателю, типу и временному срезу.
   * *Ожидание*: Строгая транзакционность при записи групп и счетчиков.

6. **Real-time Streaming Component**:
   * *Ответственность*: Управление долгоживущими соединениями (WebSocket/SSE), фильтрация входящих pub/sub сообщений под активную сессию пользователя, передача полезной нагрузки клиенту с минимальной задержкой.
   * *Ожидание*: Доставка до активного клиента < 200ms; graceful reconnect без потери целостности интерфейса.

7. **Outbound Push & Email Gateway**:
   * *Ответственность*: Формирование платформозависимых пуш-пакетов, криптографическая подпись, отправка во внешние сервисы (APNs/FCM/WebPush), адаптивная отправка email (подавление писем, если получатель активен онлайн).
   * *Ожидание*: Полная изоляция сбоев внешней сети от основной системы; автоматическая очистка устаревших токенов устройств.

### 3. Идемпотентность и стратегия дедупликации
* **Решение**: Каждое уведомление обладает естественным уникальным составным ключом `(recipient_id, activity_type, activity_id)`. Повторное событие не порождает новую запись, за исключением обновляемых типов (например, редактирование поста `status_update`), где старое уведомление замещается актуальным.

### 4. Агрегация и группировка уведомлений на уровне ядра
* **Решение**: Группировка (например, «Пользователь X и еще 5 человек оценили ваш статус») реализуется на этапе сохранения в хранилище через детерминированный составной ключ группы (`group_key`). Это снижает нагрузку на клиент и базу данных при виральных всплесках.

## Risks / Trade-offs

- **[Задержка доставки при всплесках нагрузки на очереди]** → Выделение отдельных очередей для интерактивных событий (упоминания, ответы) и отложенных реакций (массовые лайки).
- **[Потеря WebSocket-событий при обрыве соединения]** → WebSocket используется только как сигнал обновления интерфейса; источником правды остается REST API со смещением (markers / since_id).
- **[Сетевые зависания сторонних Push-провайдеров]** → Строгие сетевые таймауты (connect 2s, read 5s) в изолированных воркерах; сбой отправки пуша не откатывает факт создания нотификации.
