## ADDED Requirements

### Requirement: Сквозной сбор метрик производительности всех компонентов системы
Стенд ДОЛЖЕН (SHALL) собирать синхронизированные по времени метрики со стороны клиента (`k6`), очередей фоновых воркеров (`Sidekiq`), Mock-шлюзов и СУБД (`PostgreSQL`) для каждого из трех прогонов, исключая из финальных расчетов 60-секундную фазу прогрева.

#### Scenario: Агрегация клиентских, асинхронных и СУБД-метрик после прогона
- **WHEN** завершается любой из трех прогонов на `As-Is` или `To-Be`
- **THEN** система сохраняет:
  1) `p50`, `p95`, `p99` и долю ошибок по всем эндпоинтам чтения API v2 (раздельно для когорты «Селебрити» и «Обычные пользователи»), а также синхронную задержку эндпоинта `POST /api/v1/statuses` (для direct-сообщений);
  2) распределение сквозной задержки доставки в WebSocket (`E2E WebSocket Latency`), время ожидания в очереди и время выполнения задач воркеров (включая раздельный замер для ветки обработки личных сообщений в глубоких тредах и времени фоновой очистки `RemovalWorker`), а также счетчики доставленных пакетов Mock WebPush и SMTP (с учетом 2-минутного окна отложенной доставки писем после завершения нагрузки);
  3) снимки `pg_stat_statements` (общее время выполнения `total_exec_time`, среднее `mean_exec_time` для топ-запросов), соотношение `shared_blks_hit` к `shared_blks_read` (промахи буферного пула), ожидания блокировок строк и долю мертвых кортежей `n_dead_tup::float / NULLIF(n_live_tup + n_dead_tup, 0)` на таблице `notification_groups`;
  4) утилизацию CPU самим процессом `k6` для подтверждения отсутствия аппаратного голодания генератора нагрузки;
  5) проверку функциональной корректности и эквивалентности доставки (Delivery Parity): расчет отношения числа доставленных уведомлений к числу успешных (`201 Created`) операций записи (эквивалентно между `As-Is` и `To-Be`), с детерминированной 100% доставкой для контрольных легитимных DM-веток и 0% нефильтрованных уведомлений для спам-веток.

### Requirement: Формирование сравнительного A/B-отчета с количественными критериями победы `To-Be`
После выполнения прогонов на обоих вариантах архитектуры инструмент анализа ДОЛЖЕН (SHALL) формировать единый сравнительный отчет `As-Is vs To-Be` с формальной числовой оценкой достижения цели по зафиксированным пороговым значениям (Pass/Fail Thresholds).

#### Scenario: Автоматическая валидация количественных критериев превосходства
- **WHEN** сравниваются идентичные по `randomSeed` прогоны `As-Is` и `To-Be`
- **THEN** итоговый отчет автоматически проверяет выполнение следующих критериев:
  1) **Ускорение чтения (Прогон 1):** перцентиль `p95` времени ответа `GET /api/v2/notifications` у когорты «Селебрити» в `To-Be` снижается не менее чем в **5 раз** по сравнению с `As-Is` и не превышает **25 мс** на тестовом стенде;
  2) **Накладные расходы и защита пути записи (Прогон 1):** среднее время выполнения фонового создания обычных уведомлений (`LocalNotificationWorker`) в `To-Be` увеличивается не более чем на **5 мс** (допустимая стоимость `UPSERT`), а время обработки личных сообщений в глубоких тредах ускоряется не менее чем в **5 раз**; соблюдена эквивалентность доставки (Delivery Parity = 100%: одинаковая конверсия успешных записей в доставленные уведомления, 100% для легитимных DM и 0% для спама);
  3) **Эффективность СУБД (Прогон 1):** суммарное время выполнения запросов уведомлений (`total_exec_time`) и число промахов буферного пула (`shared_blks_read`) в PostgreSQL снижаются не менее чем в **3 раза**, а доля мертвых кортежей `n_dead_tup::float / NULLIF(n_live_tup + n_dead_tup, 0)` в таблице `notification_groups` не превышает **25%**;
  4) **Устойчивость к мутациям (Прогон 2):** удаление предзаполненного вирусного статуса с 25 000+ реакций и выполнение `RemovalWorker` завершаются без дедлоков, таймаутов блокировок и без каскадного шторма $O(N^2)$ поштучных пересчетов групп;
  5) **Пропускная способность (Прогон 3):** максимальный устойчивый RPS до нарушения целевого SLA (`p95 read <= 500 мс`, `E2E WS <= 2 000 мс`) в решении `To-Be` возрастает не менее чем в **2 раза** относительно `As-Is`.
