## ADDED Requirements

### Requirement: Высокоскоростная генерация предзаполненного датасета масштаба 5x с реалистичным перекосом
Изолированный модуль подготовки данных (Bulk Seeder) ДОЛЖЕН (SHALL) наполнять базу данных PostgreSQL без использования поштучных ORM-вызовов до эталонного масштаба 5x: 50 000 аккаунтов (`accounts`, `users`, `account_stats`, `oauth_access_tokens`) и 25 000 000 уведомлений (`notifications`) с распределением Парето, корректной ссылочной целостностью полиморфных активностей и инициализацией обязательных системных полей.

#### Scenario: Создание когорт пользователей, политик и обязательных полей авторизации
- **WHEN** запускается этап генерации пользователей и настроек
- **THEN** система создает 50 000 локальных аккаунтов со связанными записями `users` (`confirmed_at = NOW()`, `approved = true`, `disabled = false`, `current_sign_in_at = NOW()`, `last_sign_in_at = NOW()`), `account_stats`, `oauth_access_tokens` (`scopes = 'read write follow push'`, `revoked_at = NULL`, `last_used_at = NOW()`), разделенных на когорты (250 «Селебрити», 5 000 «Активных авторов / DM-участников», 44 250 «Активных читателей», 500 «Аккаунтов мутаций»), при этом:
  1) не менее 15 000 аккаунтов имеют `notification_policies` со значениями `for_private_mentions` равными `filter` (1) или `drop` (2);
  2) для 100% аккаунтов когорт «Селебрити» и «Активный читатель» создаются предзаполненные записи `markers` (`timeline = 'notifications'`, `last_read_id` вблизи верхушки ленты);
  3) для 10 000 аккаунтов создаются записи `web_push_subscriptions` с привязкой к `access_token_id`, валидными ключами P-256 (`key_p256dh`, `key_auth`), локальным адресом `endpoint` и заполненным JSON `data` (`policy: 'all'`, активные флаги `alerts` для всех типов уведомлений);
  4) для когорты оффлайн-получателей email в JSON-полях `users.settings` обязательно активируются флаги `notification_emails.favourite = true`, `notification_emails.reblog = true`, `notification_emails.follow = true`, `notification_emails.mention = true`, а также `always_send_emails = true` для форсирования доставки.

#### Scenario: Генерация вирусных постов, глубоких DM-тредов и полиморфных активностей
- **WHEN** формируется история публикаций, реакций и уведомлений объемом 25 000 000 записей
- **THEN** все сгенерированные записи укладываются по `created_at` в пределы **последних 90 дней** (`NOW() - interval '90 days' .. NOW()`), идентификаторы `statuses.id` формируются синтетическими 64-битными Snowflake-значениями с монотонным распределением эпох (исключая коллизии 16-битного счетчика `timestamp_id`), а база данных содержит:
  1) 250 вирусных статусов (от 25 000 до 50 000 реакций на каждый в 1–3 12-часовых бакетах `group_key`);
  2) для всех уведомлений `type = 'reblog'` (`activity_type = 'Status'`) создаются реальные промежуточные записи статусов-реблогов с `reblog_of_id = target_status_id`; для уведомлений `type = 'poll'` создаются связанные записи в таблице `polls` с `status_id = target_status_id`;
  3) 1 000 глубоких DM-тредов (`visibility = direct`, цепочки `in_reply_to_id` глубиной 100–500 сообщений в пределах 90 дней), где все получатели имеют политику `for_private_mentions IN (filter, drop)` и не подписаны на отправителей, при этом:
     - в 500 легитимных тредах ответ получателя расположен на глубине **50–95 сообщений вверх от листа** треда (гарантируя обнаружение до срабатывания лимита `depth_limit: 100` в `NotifyService` As-Is);
     - в 500 спам-тредах ответ получателя отсутствует, а автор листового сообщения или участник треда фиксируется как отправитель спама для прохождения проверки `StatusPolicy#show?`;
  4) от 1% до 2% авторов реакций имеют статус приостановки (`suspended_at IS NOT NULL` или `requested_deletion_at IS NOT NULL`) для верификации фильтра `Account.without_suspended`;
  5) предзаполненные записи `notification_requests` со связанными отфильтрованными уведомлениями (`filtered = true`, `group_key = NULL`) для верификации конвейера `UnfilterNotificationsWorker`;
  6) по завершении вставки данных выполняется синхронизация всех стандартных последовательностей `setval(pg_get_serial_sequence(t, 'id'), coalesce(max(id), 1))` для таблиц `notifications`, `users`, `oauth_access_tokens`, `web_push_subscriptions`, `favourites`, `mentions`, `follows`, `polls`, `conversations`, `markers`.

### Requirement: Экспорт детерминированного манифеста тестовых сущностей
После завершения генерации и построения индексов (`VACUUM ANALYZE`) модуль подготовки данных ДОЛЖЕН (SHALL) выгружать файл манифеста (`seed_manifest.json`), отделяя этап подготовки базы от генератора нагрузки.

#### Scenario: Передача входных данных генератору трафика
- **WHEN** подготовка БД успешно завершена
- **THEN** `seed_manifest.json` содержит OAuth-токена и `account_id` по всем когортам (включая изолированную когорту мутаций), идентификаторы вирусных постов (с числом реакций 25k–50k) и их авторов, список троек `(leaf_status_id, sender_account_id, recipient_acct)` для 1 000 глубоких DM-тредов (раздельно для легитимных веток с ответом на глубине 50–95 и спам-веток), идентификаторы `notification_requests` для сценария одобрения, список аккаунтов с `web_push_subscriptions` и приостановленных аккаунтов.

### Requirement: Управление эталонными «Золотыми слепками» и обязательный сброс перед прогонами
Система тестирования ДОЛЖНА (SHALL) обеспечивать строго идентичный старт для каждого испытания через механизм эталонных слепков и изоляцию мутаций.

#### Scenario: Фиксация слепков и обязательное восстановление перед каждым прогоном
- **WHEN** сидер завершает наполнение базы в схеме `As-Is`
- **THEN** создается эталонный снимок каталога данных СУБД средствами APFS Copy-on-Write (`snapshot_asis`). Для `To-Be` снимок восстанавливается, накатываются миграции `ADR-1..3` с фича-флагом `PRECOMPUTED_NOTIFICATION_GROUPS=true` и выполняется процедура Backfill с замером длительности и дискового объема таблиц `notification_groups` и `dm_thread_permissions`, после чего сохраняется слепок `snapshot_tobe`. Перед стартом КАЖДОГО из трех прогонов система в обязательном порядке восстанавливает рабочий каталог из соответствующего CoW-снимка, очищает Redis (`FLUSHDB`) строго до открытия постоянных WebSocket-соединений, выдерживает 60-секундный прогрев и вызывает `pg_stat_statements_reset()` строго по завершении прогрева перед снятием контрольных измерений.
