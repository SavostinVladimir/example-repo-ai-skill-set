## Why

Оптимизации системы уведомлений Mastodon (`ADR-1`, `ADR-2`, `ADR-3`) устраняют рекурсивные CTE и сотни подзапросов `unnest` на пути чтения, однако переносят часть стоимости на путь записи: конкурентный `UPSERT` в таблицу `notification_groups`, обновление не-HOT кортежей на вирусных постах, синхронная фиксация прав в `dm_thread_permissions` и пакетная очистка при удалении статусов. Чтобы доказательно подтвердить, что новое решение превосходит текущее (`As-Is`) без деградации записи и фоновых очередей, требуется сквозной нагрузочный тест на реалистичном объеме данных (5x) с участием всех компонентов доставки: HTTP API (`Puma`), фоновых очередей (`Sidekiq`, `NotifyService`), СУБД (`PostgreSQL`), брокера (`Redis`), WebSocket-стриминга (`Node.js`) и внешних шлюзов (`WebPush`, `SMTP`).

## What Changes

- **Раздельный генератор базы масштаба 5x и «Золотой слепок»:** Создается изолированный от генератора нагрузки модуль массовой заливки тестовой БД (50 000 аккаунтов, 25 000 000 уведомлений с перекосом по Парето, 250 вирусных постов и 1 000 глубоких DM-тредов) с гарантией ссылочной целостности полиморфных активностей, экспортом `seed_manifest.json` и механизмом эталонных слепков для идентичного старта `As-Is` и `To-Be` (включая замер этапа Backfill).
- **Односерверный тестовый стенд и легкий Mock-шлюз:** Формируется конфигурация запуска всех компонентов доставки на одной машине (10 CPU / 32 ГБ RAM) с жестким бюджетированием ресурсов (`shared_buffers = 4GB` в PostgreSQL, квоты воркеров) и легким локальным Mock-сервером для приема WebPush и SMTP с реалистичной сетевой задержкой.
- **Генератор комбинированного трафика (`k6`) и 3 тестовых прогона:** Реализуется эмуляция четырех пользовательских ролей по протоколам HTTP REST и WebSocket (включая поддержание ключей активных подписок в Redis и сквозной замер задержки доставки) в рамках трех воспроизводимых прогонов: Baseline Mixed Load, Viral Spike & Status Deletion и Stress / Breakpoint Ramp-Up.
- **Сквозная телеметрия и отчет `As-Is vs To-Be`:** Внедряется сбор метрик чтения по когортам, сквозной задержки WebSocket/Sidekiq, внутренней статистики PostgreSQL (CPU, буферный кэш/I/O, блокировки строк, MVCC bloat) и автоматическая генерация сравнительного отчета с проверкой критериев успешности.

## Capabilities

### New Capabilities
- `load-test-dataset-seeding`: Высокоскоростное наполнение БД масштаба 5x (25 млн уведомлений), экспорт манифеста тестовых сущностей и управление эталонными слепками (`As-Is` / `To-Be`).
- `load-test-environment-and-mocks`: Оркестрация всех компонентов доставки нотификаций на едином хосте с лимитами ресурсов, адаптацией тестового окружения и локальным Mock-шлюзом WebPush/SMTP.
- `load-test-traffic-scenarios`: Генерация комбинированной HTTP REST и WebSocket нагрузки по реальным пользовательским путям в трех тестовых прогонах с фиксированным `randomSeed`.
- `load-test-metrics-and-comparison`: Сбор сквозных метрик производительности конвейера и автоматическое формирование отчета сравнения `As-Is vs To-Be`.

## Impact

- **Инфраструктура нагрузочного тестирования (новые файлы):** Модуль стенда и бенчмарков (Bulk SQL-сидер, скрипты управления слепками PostgreSQL, конфиги лимитов сервисов, Mock-сервер WebPush/SMTP, сценарии `k6`, сборщик телеметрии и генератор отчета).
- **Конфигурация окружения Mastodon для стенда:** Использование `ALLOWED_PRIVATE_ADDRESSES` для локального WebPush Mock-сервера, настройка параметров `SMTP_*` для локального SMTP Mock-сервера, квоты `WEB_CONCURRENCY` / `MAX_THREADS` / `SIDEKIQ_CONCURRENCY` и тестовый initializer стенда (`config/initializers/00_load_test_bypass.rb`) для отключения троттлинга `Rack::Attack` и `RateLimiter` при флаге `LOAD_TEST_MODE=true`.
- **Архитектурный контекст:** Верифицирует решения `ADR.md` (`ADR-1`, `ADR-2`, `ADR-3`) и спецификации `notification-system-components` и `postgres-notification-optimizations`.
