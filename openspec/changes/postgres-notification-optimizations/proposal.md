## Why

Подсистема уведомлений Mastodon создаёт критическую нагрузку на PostgreSQL в трёх точках: рекурсивная группировка ленты при чтении API v2 (до 40 итераций по умолчанию и 80 при максимуме в ленте; 100 и до 1 000 в подсчёте непрочитанных), по 5 коррелированных подзапросов на группу (4 скалярных и 1 списочный — до 200 по умолчанию и 400 при максимуме) и рекурсивный обход дерева ответов глубиной до 100 шагов для антиспама личных сообщений. Предварительная материализация групп, агрегатов и разрешений тредов в PostgreSQL снизит p95 SQL-латентность целевых запросов чтения и подсчёта непрочитанных со 150–500 мс до 1–5 мс (end-to-end HTTP p95 `<= 25 мс` для ленты API v2), проверку входящих DM до `< 0.2 мс` и сократит Read CPU и дисковый I/O целевых запросов на порядок (общее снижение нагрузки подсистемы в БД `>= 3x` при оверхеде записи `<= +5 мс` p95) с сохранением контрактов API и гарантий безопасности.

## What Changes

- **Сценарий 1 (Write-Time Grouping для пагинации API v2):** Вводится таблица `notification_groups` для транзакционной материализации групп при записи и разблокировке из карантина с поддержкой фильтрации по типам, блокировкам и суспендам, двунаправленной курсорной пагинации, прозрачного чтения истории за горизонтом материализации и динамической канарейки.
- **Сценарий 2 (Материализация агрегатов групп):** В `notification_groups` хранятся счётчик уведомлений, дедуплицированный список последних авторов и граничные курсоры, что устраняет до 200–400 коррелированных подзапросов при чтении, сохраняет точные постраничные курсоры в списке и одиночном просмотре, а также обеспечивает консистентную очистку и пересчёт при скрытии групп, очистке ленты, отмене реакций, редактировании и удалении статусов и аккаунтов.
- **Сценарий 3 (Индексированный реестр разрешений DM-тредов):** Вводится таблица `dm_thread_permissions` с полным историческим бэкфиллом для синхронной фиксации исходящих разрешений при публикации и редактировании DM, заменяющая рекурсивный обход предков на проверку за $O(1)$ в контексте родительского диалога с защитой от спуфинга и групповой инъекции.

## Non-Goals

- Изменение форматов ответов REST API v1/v2, WebSocket Streaming и клиентов.
- Вынос хранилища, очередей агрегации или счётчиков уведомлений в Redis или внешние NoSQL СУБД (`ADR-1`, `ADR-2`).
- Изменение правил 12-часового окна группировки.

## Capabilities

### New Capabilities
- `notification-groups-pagination`: Материализация и плоская индексная пагинация сгруппированных уведомлений в PostgreSQL (`notification_groups`) взамен рекурсивного чтения.
- `notification-groups-aggregates`: Предвычисление, хранение и консистентная инвалидация агрегатов группы взамен множественных коррелированных подзапросов.
- `dm-thread-permissions`: Индексированная проверка права на ответ в личной переписке через `dm_thread_permissions` взамен рекурсивного обхода предков.

## Impact

- **Схема БД и миграции:** Новые таблицы `notification_groups` и `dm_thread_permissions`, индексы пагинации, пересчёта и очистки, политика retention/pruning.
- **Доменный слой и сервисы:** Модели уведомлений, статусов и аккаунтов; сервисы публикации, редактирования, удаления статусов, уведомлений и модерации (блокировки аккаунтов и доменов, суспенд, удаление).
- **Фоновые воркеры и эксплуатация:** Воркеры доставки, разблокировки, разрешения тредов, фонового пересчёта и скрытия крупных групп; задачи бэкфилла, shadow-reconciliation, метрики Prometheus (`prometheus_exporter`) / OpenTelemetry и динамические рубильники в Redis.
- **API v1/v2:** Контроллеры уведомлений, презентер и сериализаторы групп.
- **Реестр архитектурных решений:** `ADR.md` (`ADR-1`, `ADR-2`, `ADR-4`).
